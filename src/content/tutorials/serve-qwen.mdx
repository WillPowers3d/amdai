## Path A — llama-server (least pain)

Daily driver: Unsloth **UD-Q5_K_XL** (Q5 family — do not drop to Q3 to “make it fit”). Vulkan binary (`build-vk`) is what we run; HIP (`build`) is fine if that is the tree you compiled.

**not recorded:** exact command line / measured VRAM from rig owner.

```bash
./build-vk/bin/llama-server \
  -m ~/models/Qwen3.6-35B-A3B-UD-Q5_K_XL.gguf \
  -ngl 99 \
  -c 262144 \
  --cache-type-k f16 \
  --cache-type-v f16 \
  --jinja \
  --host 127.0.0.1 \
  --port 8080
```

`--jinja` matters on current Qwen templates.

```bash
watch -n1 rocm-smi
curl -s http://127.0.0.1:8080/v1/models
curl -s http://127.0.0.1:8080/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{"model":"qwen","messages":[{"role":"user","content":"Reply with the single word READY and nothing else."}],"max_tokens":8}'
```

If VRAM never moves, stop. Point Hermes or OpenClaw at `http://127.0.0.1:8080/v1` **only after** this returns `READY`.

## Path B — Strata (fast agent on our rig)

When the daily driver is boring and you want the Flash stack: **Qwen 3.8 Flash** Unsloth **UD-Q6_K_XL** on **Strata v0.1.42** at 262K. Measured on our test rig ~32.6 tok/s versus llama.cpp ~16 tok/s. llama.cpp Q6 is the fallback.

Publisher UD-Q6_K_XL listing is ~169 GB — the [calculator](/calculator) will show RAM overflow on one 32 GB card. **not recorded:** exact flags / measured VRAM+RAM from rig owner.

Cards: [stacks](/stacks).

<h2 id="advanced-vllm">Advanced — vLLM (not the consumer default)</h2>

Two pins. Do not mix them in one venv. The [weekly card](/) is the current recommendation.

**Reliability (`qwen-reliable`) is llama.cpp, not vLLM.** AMD-aligned vLLM **0.27** / ROCm 10 remains the conservative supported combo (docs snapshot: vLLM **0.27** + PyTorch **2.13**). Copy the current image tag from [AMD’s vLLM page](https://rocm.docs.amd.com/projects/ai-ecosystem/en/latest/inference/vllm.html) if you serve HF weights.

**Community / ROCm Docker — vLLM 0.31 try**

Engine try-tag only. Previous try-tag `v0.30.0` is still valid if 0.31 misbehaves. Do not replace the daily-driver GGUF path with this.

```bash
# Community ROCm image — NOT default PyPI
# not recorded: confirm the current 0.31-class tag on Docker Hub / the weekly card
docker pull vllm/vllm-openai-rocm:v0.30.0
# previous: vllm/vllm-openai-rocm:v0.29.0
# previous wheels: pip install vllm --extra-index-url https://wheels.vllm.ai/rocm/0.29.0/rocm723
```

```bash
# Image tags change. Confirm against AMD or vLLM / Docker Hub.
docker run --rm -it \
  --device /dev/kfd --device /dev/dri \
  --group-add video --ipc=host --network host \
  -v "$HOME/models:/models" \
  vllm/vllm-openai-rocm:v0.30.0 \
  --model /models/YOUR-QWEN-HF \
  --host 127.0.0.1 --port 8000
```

<Callout type="warn">
`pip install vllm` with no extra index is **CUDA**. If import looks NVIDIA-shaped, you installed the wrong wheel.
</Callout>

ROCm CLI v0.2.0 documents `rocm install vllm` for 10.1 wheels — that is an [install claim](https://github.com/ROCm/rocm-cli/releases/tag/v0.2.0), not a first-party bench. [Version matrix](/updates/matrix).

```bash
curl -s http://127.0.0.1:8000/v1/models
```

OpenClaw’s vLLM provider wants `http://127.0.0.1:8000/v1` and `VLLM_API_KEY` set (dummy is fine if the server does not auth).

## Golden checks

1. Short `READY` completion.
2. A second turn that stays in-template.
3. `rocm-smi` during both.
4. Then: harness tools. Then, if you still want it, a second weight (coder / abliterated).

If thinking never ends, stay on official instruct with thinking off, or fix `--jinja`. Do not “fix” it by grabbing a random uncensored GGUF.
